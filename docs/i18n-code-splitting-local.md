# Safe I18N Code Splitting — Local ReportDate: 2026-11-07URL: http://localhost:8275No commit, push, PR, merge, deploy, or migration performed.## Analysis- `i18n.js` (104KB) exports `extraCopy` with `vi`, `en`, `jp` objects, then merges them into `copy` via `Object.assign` at module load.- `app-config.js` imports `extraCopy` synchronously and merges all three languages before `copy` is used.- `app.js` uses `t(key) { return copy[this.lang][key] || copy.vi[key] || key; }` synchronously across all views.- Language is chosen from `localStorage('paradox-lang')` in the `EduApp` constructor, and switching calls `this.render()` immediately.## Feasibility AssessmentSafe i18n code splitting is **not implemented**.Reason: splitting by language requires either:1. Making `copy`/`t()` asynchronous or lazy, which touches every view and template literal that calls `this.t(...)`, or2. Loading only the active language before first render and fetching others on switch, which requires restructuring `app-config.js` merge logic and ensuring `copy[lang]` is populated before any render.Both options change the synchronous translation API on a wide surface and risk raw translation keys appearing during loading. Per the safety-first instruction, this refactor was not attempted.## Estimated Impact (if implemented later)- Initial bundle reduction: ~66KB (en + jp) if default language is vi.- LCP improvement: modest (JS execution is ~75ms; module loading/render delay is the dominant factor).- Risk: medium (translation key fallback, loading flash, language switching race conditions).## Recommendation1. Keep current i18n bundle as-is for stability.2.
