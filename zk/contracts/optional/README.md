# Optional Avalanche adapter (reference only)

`PARADOXZKCredentialAdapter.sol` shows how the Groth16 proof could be linked to
the existing `LearningCredentialRegistry` on Avalanche Fuji.

**Not deployed. Not compiled against Fuji. Not audited.**

The adapter expects the verifier contract generated by `npm run build`:

```
zk/build/Groth16Verifier.sol
```

That generated contract is not committed because it is derived from the local
development trusted setup. In a real deployment, generate it from the production
zkey, audit it, and deploy it before the adapter.

## Trust boundary (important)

This adapter does **not** verify the Ed25519 evaluator attestation. It only
accepts proofs from `authorizedVerifier`, which must verify the attestation,
evaluation ID, learner binding and freshness off-chain first.

It is a **trusted-relayer binding**, not trustless on-chain AI verification.
For trustless on-chain verification, add EIP-712/secp256k1 attestation
verification to the adapter (see docs §7).

## On-chain checks performed by the adapter

1. `msg.sender` is the authorized issuer/relayer.
2. The credential exists and is not revoked in the registry.
3. The registry evidence hash equals the evidence hash supplied.
4. Public signal `evidenceHash` equals
   `sha256("paradox-zk-proof-of-learning-v1|evidence|" || evidenceHash) % p`.
5. Public signal `credentialIdHash` equals
   `sha256("paradox-zk-proof-of-learning-v1|credential-id|" || credentialId) % p`.
6. Public signals `evaluationIdHash` and `learnerBinding` match the values pinned
   by the relayer.
7. The public threshold meets `policyThreshold` and is <= 100.
8. The Groth16 proof verifies.
9. The credential has no previous conflicting commitment; repeated verification
   with the same commitment is idempotent and emits no duplicate event.

## Checks intentionally left off-chain

- Ed25519 evaluator attestation (no native precompile; use an authorized issuer
  or switch to EIP-712/secp256k1).
- Attestation freshness, revocation of the evaluator key, and nullifier policy.
- That the evidence hash is actually the SHA-256 of the submitted learning
  evidence (the issuer/registry is responsible for that semantic check).

See `docs/ZK-PROOF-OF-LEARNING.md` §7 and `docs/SECURITY-REVIEW-OP2.md`.
